# TODO: ролевая модель и авторизация сотрудников (roadmap, не реализовано)

Зафиксировано по итогам обсуждения в сессии — база (`plugins/employees`,
таблица `employees`) уже реализована и используется (created_by/updated_by,
селектор "текущего сотрудника"), но **без реальной авторизации**: нет пароля,
нет проверки полномочий, поле `role` существует в схеме, но у всех сотрудников
значение `"all"` и нигде не проверяется. Этот документ — план того, что
достраивать, когда (если) понадобится реальное разграничение прав.

## Что уже есть (готовая база)

- `database.sqlalchemy_models.Employee`: `id`, `full_name`, `login` (уникален),
  `phone`, `position`, `role` (пока всегда `"all"`), `is_active`,
  `created_by_id`/`updated_by_id` (self-referencing FK), `created_at`/`updated_at`.
- `plugins/employees` — второй реальный плагин ядра (после `plugins/clients`):
  `EmployeeEntity`, `IEmployeeRepository` + `SqlAlchemyEmployeeRepository`,
  `EmployeeService` (CRUD + "текущий сотрудник" на время работы процесса).
- `EmployeeService.has_permission(employee_id, permission) -> bool` —
  **заглушка, всегда `True`**. Единственная точка входа, через которую
  остальной код МОЖЕТ уже сейчас спрашивать "можно ли этому сотруднику Х" —
  расставлять вызовы этого метода в GUI/PWA можно уже сейчас, не дожидаясь
  реализации ролей: когда роли появятся, изменится только тело метода, а не
  вызывающий код.
- `plugins/employees/login_generator.py` — генерация логина по ФИО
  (транслитерация, SAP-стиль фамилия+инициалы, обработка коллизий).
- Простое "переключение учётки" в GUI (дропдаун "ФИО — логин" в шапке
  главного окна) — БЕЗ пароля, любой может выбрать любого сотрудника.
- `core.base.PermissionObject` + `core.base.PermissionAwareMixin` (вшит в
  `BaseService`/`BaseRepository`) — декларативный каркас по аналогии с
  объектом авторизации SAP (SU21/PFCG): сервис объявляет классовым атрибутом
  `permission_object = PermissionObject(name=..., operations=(...), table=...)`,
  указывая ИМЯ объекта полномочий, допустимые операции и таблицу БД, которой
  он соответствует. Уже объявлено (как пример/каркас, БЕЗ проверки) в
  `ClientService.permission_object` ("CLIENTS") и
  `EmployeeService.permission_object` ("EMPLOYEES"). Сам по себе ничего не
  проверяет — только декларация, на которую сядет будущий enforcement.

## Целевой дизайн (когда понадобится реальная авторизация)

По аналогии с SAP (SU01 — пользователь, PFCG — роли, объекты авторизации на
мандант): не хранить права как единственную строку `role` на сотруднике, а
завести отдельную сущность "роль" с явным перечнем полномочий, и связь
сотрудник↔роль (обычно many-to-many — у сотрудника может быть >1 роли).

### Схема (новые таблицы)

```
roles
  id, name (уникально, напр. "manager", "engineer", "viewer"), description

permissions
  id, code (уникально, напр. "devices.create", "devices.delete",
            "finances.view", "employees.manage"), description

role_permissions   (many-to-many roles<->permissions)
  role_id, permission_id

employee_roles     (many-to-many employees<->roles — не одно поле role!)
  employee_id, role_id
```

Модель полномочий — простые строковые коды `"<модуль>.<действие>"`
(`devices.create`, `devices.edit`, `devices.delete`, `finances.view`,
`employees.manage`, `settings.manage`, …), а не общая ролевая иерархия —
проще проверять (`permission_code in employee_permissions`), проще
расширять (добавить новый код — не трогать существующие роли).

### Пароль и первый вход

- При создании сотрудника — генерируется временный пароль (случайный,
  показывается один раз в диалоге создания — как временный пароль в SAP при
  создании пользователя), хэшируется (например `bcrypt`/`argon2`, НЕ md5/sha1
  без соли) и сохраняется вместе с флагом `must_change_password = True`.
- При первом входе с этим паролем — обязательная смена (форма "новый
  пароль" перед тем, как пустить дальше), `must_change_password` сбрасывается.
- Экран "выбора учётки" (текущий дропдаун без пароля) заменяется формой
  логин+пароль — тот момент, когда `EmployeesManagerWindow`/переключатель в
  main_window.py потребуют реального изменения, не только фоновой модели.

### Проверка полномочий (enforcement)

- `permission_code` в формате `"<PermissionObject.name>.<операция>"`
  (напр. `"DEVICES.delete"`, `"EMPLOYEES.manage_roles"`) — коды операций
  берутся из `PermissionObject.operations` уже объявленного сервиса, а не
  придумываются заново на месте enforcement.
- `EmployeeService.has_permission(employee_id, permission_code)` — тело
  заменяется на реальный запрос: собрать все роли сотрудника → все
  permissions этих ролей → проверить наличие `permission_code`.
- Точки вызова (расставить постепенно, не всё сразу):
  - GUI: перед открытием диалогов создания/удаления заказа, управления
    сотрудниками, финансовых отчётов — если `not has_permission(...)`, кнопка
    неактивна или показывается предупреждение вместо открытия окна.
  - PWA: `require_api_key` decorator расширяется/дополняется
    `require_permission(code)` — после проверки ключа проверяет, что
    сотрудник, чей логин передан в запросе (потребуется передавать логин в
    запросе, раз PWA сейчас не привязан к "текущему сотруднику" десктопа),
    имеет нужное право.
- **Не проверять права там, где это не имеет смысла** — например,
  просмотр собственного профиля, генератор логина — только там, где
  разграничение реально нужно бизнесу (создание/удаление финансовых записей,
  управление сотрудниками, экспорт данных).

### Admin-панель

- Новый диалог (или вкладка в `EmployeesManagerWindow`) — управление ролями:
  список ролей, чекбоксы permissions на роль, назначение ролей сотруднику
  (мульти-select, не одно поле).
- Видна/доступна только сотрудникам с правом `employees.manage_roles` —
  то есть после того, как enforcement уже работает (курица-яйцо: первая роль
  с этим правом создаётся миграцией/сидом при раскатке, не через UI).

## Порядок внедрения (когда решим делать)

1. Схема (roles/permissions/role_permissions/employee_roles) +
   `database/sqlalchemy_models.py` + миграция существующих `role="all"`
   сотрудников в роль "admin" со всеми правами (чтобы никто не потерял
   доступ при включении enforcement).
2. Пароль + хэширование + `must_change_password` + форма первого входа.
3. Реальное тело `has_permission()` (пока заглушка — правки не потребуются
   у вызывающего кода, если он уже использует этот метод).
4. Точки enforcement в GUI (по одной, начиная с самых чувствительных —
   удаление, финансы, управление сотрудниками).
5. Точки enforcement в PWA (`require_permission`).
6. Admin-панель управления ролями.

## Явно НЕ в этом плане

- OAuth/SSO/внешние провайдеры аутентификации — оверкилл для локального
  десктоп-приложения одного сервисного центра.
- Мульти-тенантность (несколько "мандантов" в одной БД) — приложение
  однопользовательское/одноцентровое, `role_permissions`/`employee_roles`
  не нуждаются в поле "мандант", в отличие от SAP-аналогии, которая была
  ориентиром только для терминологии ролей/полномочий.
