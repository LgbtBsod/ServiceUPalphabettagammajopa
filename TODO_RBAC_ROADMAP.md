## Целевой дизайн (когда понадобится реальная авторизация)

По аналогии с SAP (SU01 — пользователь, PFCG — роли, объекты авторизации на
мандант): не хранить права как единственную строку `role` на сотруднике, а
завести отдельную сущность "роль" с явным перечнем полномочий, и связь
сотрудник↔роль (обычно many-to-many — у сотрудника может быть >1 роли).

### Схема (новые таблицы)

```
roles
  id, name (уникально, напр. "manager", "engineer", "viewer"), description

permissions
  id, code (уникально, напр. "devices.create", "devices.delete",
            "finances.view", "employees.manage"), description

role_permissions   (many-to-many roles<->permissions)
  role_id, permission_id

employee_roles     (many-to-many employees<->roles — не одно поле role!)
  employee_id, role_id
```

Модель полномочий — простые строковые коды `"<модуль>.<действие>"`
(`devices.create`, `devices.edit`, `devices.delete`, `finances.view`,
`employees.manage`, `settings.manage`, …), а не общая ролевая иерархия —
проще проверять (`permission_code in employee_permissions`), проще
расширять (добавить новый код — не трогать существующие роли).

### Пароль и первый вход

- При создании сотрудника — генерируется временный пароль (случайный,
  показывается один раз в диалоге создания — как временный пароль в SAP при
  создании пользователя), хэшируется (например `bcrypt`/`argon2`, НЕ md5/sha1
  без соли) и сохраняется вместе с флагом `must_change_password = True`.
- При первом входе с этим паролем — обязательная смена (форма "новый
  пароль" перед тем, как пустить дальше), `must_change_password` сбрасывается.
- Экран "выбора учётки" (текущий дропдаун без пароля) заменяется формой
  логин+пароль — тот момент, когда `EmployeesManagerWindow`/переключатель в
  main_window.py потребуют реального изменения, не только фоновой модели.

### Проверка полномочий (enforcement)

- `permission_code` в формате `"<PermissionObject.name>.<операция>"`
  (напр. `"DEVICES.delete"`, `"EMPLOYEES.manage_roles"`) — коды операций
  берутся из `PermissionObject.operations` уже объявленного сервиса, а не
  придумываются заново на месте enforcement.
- `EmployeeService.has_permission(employee_id, permission_code)` — тело
  заменяется на реальный запрос: собрать все роли сотрудника → все
  permissions этих ролей → проверить наличие `permission_code`.
- Точки вызова (расставить постепенно, не всё сразу):
  - GUI: перед открытием диалогов создания/удаления заказа, управления
    сотрудниками, финансовых отчётов — если `not has_permission(...)`, кнопка
    неактивна или показывается предупреждение вместо открытия окна.
  - PWA: `require_api_key` decorator расширяется/дополняется
    `require_permission(code)` — после проверки ключа проверяет, что
    сотрудник, чей логин передан в запросе (потребуется передавать логин в
    запросе, раз PWA сейчас не привязан к "текущему сотруднику" десктопа),
    имеет нужное право.
- **Не проверять права там, где это не имеет смысла** — например,
  просмотр собственного профиля, генератор логина — только там, где
  разграничение реально нужно бизнесу (создание/удаление финансовых записей,
  управление сотрудниками, экспорт данных).

## Явно НЕ в этом плане

- OAuth/SSO/внешние провайдеры аутентификации — оверкилл для локального
  десктоп-приложения одного сервисного центра.
- Мульти-тенантность (несколько "мандантов" в одной БД) — приложение
  однопользовательское/одноцентровое, `role_permissions`/`employee_roles`
  не нуждаются в поле "мандант", в отличие от SAP-аналогии, которая была
  ориентиром только для терминологии ролей/полномочий.
